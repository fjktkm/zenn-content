## 1. はじめに

Google Fonts には数千ものフォントが収録されています．これらを使うときは，必要なフォントを選んで個別にインストールするのが普通です．

しかし，フォントには複数のフォントを一つのファイルに格納する **TrueType Collection（TTC）** という形式があります．それなら，Google Fonts のフォントをすべて一つの TTC ファイルにまとめることもできるのではないでしょうか．

タイトルでは簡単のため「全部入りフォント」と呼んでいますが，厳密には一つのフォントを作ったわけではありません．複数のフォントを収録した一つの **フォントファイル** を作るという内容です．

そこで，実際にやってみました．

**一つの TTC ファイルを作ること自体はできました**．ただし，単に束ねるだけでは Windows で扱えず，ファイルサイズやメタデータ，さらにはライセンスにも向き合うことになりました．

## 2. 方法

### 2.1. TrueType Collection

TTC はフォントファイルを単純に連結したものではありません．先頭に各フォントへのオフセットを記録し，複数のフォントで同一のテーブルを共有できる構造になっています．通常は太さの異なる複数のスタイルなどをまとめるために使われます．今回はその本来の規模を大幅に超えて，Google Fonts 全体を一つのコレクションにします．実用性よりも「形式上できるのか」を確かめる実験です．

### 2.2. 対象のフォント

Google Fonts の公式リポジトリから，`apache`，`ofl`，`ufl` 以下にある各ファミリーディレクトリ直下の `.ttf` と `.otf` を収集しました．サブディレクトリに置かれた別ビルドは除外しています．

検証時点の対象は **2,048 ファミリー，3,793 ファイル** でした．ライセンス別の内訳は次のとおりです．

| ライセンス            | ファイル数 |
| --------------------- | ---------: |
| SIL Open Font License |      3,715 |
| Apache License 2.0    |         61 |
| Ubuntu Font Licence   |         17 |

### 2.3. 素朴な実装

TTC の生成には Python の `fontTools` を使いました．中心となる処理だけを抜き出すと，次のようになります．

```python
from fontTools.ttLib import TTCollection, TTFont

collection = TTCollection()
collection.fonts = [
    TTFont(path, lazy=True, recalcTimestamp=False) for path in font_paths
]
collection.save("output/google-fonts.ttc", shareTables=True)
```

`TTCollection` にすべての `TTFont` を渡して保存するだけなので，生成そのものは驚くほど簡単です．`shareTables=True` にすると，同じ内容のテーブルがコレクション内で共有されます．また，`recalcTimestamp=False` とすることでビルド時刻による差分を避けています．

## 3. 問題点

素朴な方法で生成した TTC を Windows のフォントビューアーで開こうとしましたが，正常に開くことができませんでした．そこで，対象とするフォントを減らしながら原因を調べました．

### 3.1. Gidugu-Regular.ttf

フォント数を減らした TTC は正常に開くことができました．対象を変えながら検証したところ，`Gidugu-Regular.ttf` が含まれている場合に開けなくなることがわかりました．

調べてみると，`Gidugu-Regular.ttf` が Windows で有効なフォントとして認識されず，インストールできない問題が Google Fonts の Issue に報告されていました．

https://github.com/google/fonts/issues/9982

そこでこの問題の原因を調べたところ，`Gidugu-Regular.ttf` の `name` テーブルに Windows 向けの **Name ID 3（Unique font identifier）** レコードがないことがわかりました．

### 3.2. 2 GiB の壁

`Gidugu-Regular.ttf` の Name ID 3 を補完し，あらためて Google Fonts 全体を対象に TTC を生成しました．しかし，それでもフォントビューアーで開くことはできませんでした．フォント数を減らした TTC は開けることから，今度はファイルサイズに原因があると考えました．

OpenType の TTC では各フォントへのオフセットが符号なし 32 bit 整数で表現されるため，形式上は 4 GiB 付近まで表現できます．一方，Windows GDI の `AddFontResourceExW` を使い，TTC の末尾にデータを足しながら境界を調べたところ，次の結果になりました．

| TTC のサイズ       | 結果 |
| ------------------ | ---- |
| 2,147,483,647 byte | 成功 |
| 2,147,483,648 byte | 失敗 |

境界はちょうど $2^{31}$ byte，**2 GiB** でした．これは OpenType 形式そのものの上限ではなく，Windows の実装上の制限と考えられます．Windows でも開ける成果物にするには，Google Fonts 全体をこのサイズ未満に収める必要があります．

## 4. 解決策

### 4.1. Name ID 3 を補完する

Name ID 3 がない場合に限り，既存のバージョン，ベンダー ID，PostScript 名から一般的な形式の識別子を組み立て，TTC の生成時に追加します．

```python
version = names.getName(5, 3, 1, 0x0409).toUnicode()
version = version.removeprefix("Version ").split(";", 1)[0]
postscript_name = names.getName(6, 3, 1, 0x0409).toUnicode()
vendor = font["OS/2"].achVendID.strip()
unique_id = f"{version};{vendor};{postscript_name}"

names.setName(unique_id, 3, 3, 1, 0x0409)
```

この変更はメモリ上のフォントに対して行い，Google Fonts から取得した元ファイル自体は変更していません．

### 4.2. HarfBuzz Subset で縮める

すべてのフォントを TTC に格納する前に HarfBuzz Subset へ通しました．Subset という名前ですが，今回は Unicode コードポイントとグリフを全範囲指定しているため，収録文字を間引くことが目的ではありません．

```python
face = hb.Face(hb.Blob.from_file_path(path))
subset_input = hb.SubsetInput()
subset_input.unicode_set.add_range(0, 0x10FFFF)
subset_input.glyph_set.add_range(0, face.glyph_count - 1)
subset_input.flags |= hb.SubsetFlags.NO_HINTING | hb.SubsetFlags.OPTIMIZE_IUP_DELTAS

font_data = subset_input.subset(face).blob.data
```

ここでは主に，TrueType のヒンティング情報を削除し，バリアブルフォントの IUP delta を最適化しています．そのほかは HarfBuzz のデフォルトのサブセット方針に従います．

一方，SVG テーブルは HarfBuzz Subset で処理できないため，削除せずそのまま保持しました．古い `kern` テーブルも，同じ役割を果たす GPOS テーブルがない場合に限って保持します．これは fontTools のデフォルトの挙動に合わせたものです．

```python
subset_input.drop_table_tag_set.discard(SVG)
subset_input.no_subset_table_tag_set.add(SVG)

if GPOS not in face.table_tags:
    subset_input.drop_table_tag_set.discard(KERN)
    subset_input.no_subset_table_tag_set.add(KERN)
```

これにより，文字とグリフを維持したまま Windows の 2 GiB 制限を下回る **約 1.93 GiB** の TTC を生成できました．

## 5. 動作確認

### 5.1. フォントビューアーで開く

完成した TTC を Windows のフォントビューアーで開いてみました．ウィンドウが表示されて操作可能になるまでの時間を 3 回計測したところ，5.01 秒，4.95 秒，4.93 秒で，平均は 4.96 秒でした．約 1.93 GiB のフォントファイルが 5 秒ほどで開けたのは意外な結果でした．

![](/images/95ec94e1c2ab38/windows-font-viewer.png)
_Windows のフォントビューアーで開いた様子_

最初に表示されたのは `Aclonica` です．右上の「次へ」を押すと，TTC に収録されたフォントを順番に表示できます．ここまでは通常の TTC と変わりません．

面白いのはウィンドウのタイトルです．フォントビューアーは TTC に収録されたフォント名を `&` で連結してタイトルに設定するようで，3,793 個のフォント名を並べたとんでもなく長いタイトルができあがりました．画面上では当然収まりきらず，途中のごく一部だけが表示されています．世界最大級のフォントファイルは，ウィンドウタイトルまで巨大になりました．

### 5.2. インストールする

次に，フォントビューアーから TTC を実際にインストールしました．約 1.93 GiB のファイルですが，コピーと登録は約 5 秒で完了しました．

インストール前に Windows の設定アプリで確認すると，使用可能なフォントは 334 個でした．

![](/images/95ec94e1c2ab38/fonts-before-install.png)
_TTC をインストールする前のフォント一覧_

インストール後は 2,464 個まで増えました．一つの TTC ファイルをインストールしただけで，フォント一覧に 2,130 個も追加されたことになります．Google Fonts のファミリー数である 2,048 とは一致しませんが，これは Google Fonts のディレクトリと Windows のフォント一覧でグループ化の単位が異なるためだと考えられます．

![](/images/95ec94e1c2ab38/fonts-after-install.png)
_TTC をインストールした後のフォント一覧_

一覧から `Aclonica` を開いてメタデータを確認すると，フォントファイルとして `google-fonts.ttc` が表示されました．TTC に収録されたフォントが個別のフォントファイルへ展開されたわけではなく，一つの TTC を参照するフォントとして Windows に登録されていることがわかります．

![](/images/95ec94e1c2ab38/font-details-aclonica.png)
_Aclonica のフォントファイルとして google-fonts.ttc が表示される_

### 5.3. アンインストールする

また，この画面から `Aclonica` 一つだけをアンインストールしようとすると，「フォント コレクション全体」を削除するか確認されました．TTC に収録されたフォントは個別にアンインストールできず，一つを削除しようとすると 3,793 個すべてがまとめてアンインストールされるようです．全部入りにした結果，削除するときまで全部一緒になりました．

![](/images/95ec94e1c2ab38/uninstall-font-collection-dialog.png)

## 6. 考察

### 6.1. サイズの制約

完成した TTC は約 1.93 GiB で，Windows の 2 GiB 制限まで約 68 MiB しか残っていません．今回は HarfBuzz Subset による最適化で制限を下回りましたが，Google Fonts に新しいフォントが追加されれば，いずれ単一の TTC には収まらなくなると考えられます．

Windows との互換性を維持したまま今後もすべての Google Fonts を格納するには，複数の TTC に分割する，収録対象を限定する，さらにフォントを小さくするなどの対応が必要になります．Google Fonts 全部入りの「一つの」フォントファイルは，少なくとも Windows 上では限界に近いところで成立しています．

### 6.2. ライセンス

TTC の生成には成功しましたが，生成した `google-fonts.ttc` は配布物にできませんでした．これは単に巨大だからではなく，ライセンス上の条件を満たしていないためです．

今回の処理ではヒンティングの削除やテーブルの書き換えを行っており，元のフォントに変更を加えています．

- SIL Open Font License の対象には Reserved Font Name を宣言するファミリーがあり，変更版で元の名称を使うには条件があります．今回の対象では少なくとも 555 ファミリーが該当します．
- Apache License 2.0 のフォントを再配布するには，ライセンスや通知を同梱し，変更したファイルにはその旨を明示する必要があります．今回のビルドではそのための付属資料を生成していません．
- Ubuntu Font Licence の対象となる 5 ファミリーは，変換・最適化した生成物を Modified Version として扱う必要がありますが，今回のビルドでは派生物を区別する名称を付けていません．

さらに，HarfBuzz のデフォルト処理では，作者名，ベンダー名，プロジェクト URL など，一部の必須ではない `name` レコードが削除されることがあります．著作権レコードは保持されるものの，ファミリーごとのライセンスファイルや通知が TTC に埋め込まれるわけではありません．

したがって，生成できることと，再配布できることは別問題です．手元で試す場合も，各フォントのライセンスに従う必要があります．

## 7. おわりに

Google Fonts の 3,793 ファイルを一つの TrueType Collection にまとめました．TTC の生成 API 自体は単純でしたが，Windows で実際に扱えるようにし，生成物の扱いまで検討するには，次の対応が必要でした．

- `Gidugu-Regular.ttf` に欠落していた Name ID 3 の補完
- 2 GiB 未満に収めるための HarfBuzz Subset による最適化
- SVG や legacy `kern` テーブルを保持するための例外処理
- 各フォントのライセンスを踏まえた生成物の非配布

「全部まとめたらどうなるだろう」という思いつきから始めた実験でしたが，フォント形式の仕様，OS の実装上の制約，個々のフォントの差異，ライセンスと，フォントを取り巻く複数の層を一度に見ることができました．一つのファイルにはできても，それを一つのフォントのように気軽に扱えるわけではない，というのが今回の結論です．
